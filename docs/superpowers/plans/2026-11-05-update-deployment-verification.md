# 업데이트 배포·복구 검증 계획

목표: 0.4.42 main(cf18098)의 기존 자동 업데이트 경로를 보존하면서 확장 재시도 중단, 복구 신호 유실, 잘못된 콘텐츠 빌드 표식과 자동 롤백의 데이터 호환성 누락을 재현·수정한다.

범위: 중앙 업데이트 작업자, 확장 업데이트 확인, 배포 검사. 자동 오류 제보 수집·전송 및 발송 코어는 변경하지 않는다. 사용자 Discord 발송과 운영 설정 변경은 수행하지 않는다.

1. `tests/central-extension-update-reliability.test.js`: 3회 초과 재시도, 워커 재생성 후 대기 유지, 바쁜 시점의 복구 신호 보존, 정상 로드 후 표식 정리를 먼저 실패시킨다. `central/extension/update.js`에서 기존 heartbeat를 이용해 30초~5분 지연으로 계속 복구한다. 안전 상태·중복 reload 방지는 유지한다.
2. `tests/central-extension-version-build.test.js`: 실제 빌드 파일의 콘텐츠 버전/빌드 표식 훼손을 검사에서 거절하도록 재현한다. `scripts/check-central.mjs`와 `central/host/extension-update.mjs`에서 manifest, 콘텐츠 버전, 해시를 검증한다.
3. `tests/central-updater.test.js`: 새 앱 시작 실패 후 현재 DB를 읽지 못하는 이전 코드의 자동 복귀를 거절하도록 재현한다. `central/runtime/updater.mjs`에서 기존 복제 DB 호환성 검사를 자동 롤백에도 적용한다. 호환 실패 시 DB와 두 코드 사본을 보존한다.
4. 임시 설치 디렉터리에서 실제 중앙 런타임 업데이트·실패 복귀·롤백과 계정/채널/문구/그룹 보존을 검증한다. 실제 브라우저는 사용하지 않는다.
5. 전체 테스트·TypeScript·프로덕션 빌드·배포 검사를 수행하고 독립 리뷰 후 GitHub PR을 만든다. 발행 직전 main 및 진행 중 PR을 다시 확인한다.

검토 초점: 로컬/중앙이 바쁠 때 복구 신호, 강제 확인의 대기 우회, 같은 버전 다른 빌드, 시작 실패 뒤 DB 변경, 실제 운영 PC 미접근과 코드 검증의 구분.

초기 근거: Mac mini에 DICO 운영 데이터 디렉터리 없음. 제보 서버 실행 중이며 `email-update` 소스는 a2a7a20, 미커밋 변경 없음. 별도 clone 사용. 의존성 설치 뒤 main 전체 1,269개 통과.


## 실행 기록

- 확장 실패 대기/복구 신호, 콘텐츠 표식 훼손, 비호환 자동 롤백 회귀의 수정 전 실패와 수정 후 통과를 확인했다.
- 독립 리뷰의 2건(새 복구 신호의 대기 초기화, 콘텐츠 상태 조회의 복구 신호 유실)을 실제 함수 실행 회귀로 재현·수정했다.
- Linux와 macOS의 실제 격리 중앙 프로세스 시험 통과. cf18098 실코드 worker를 사용한 macOS 이행·복귀 2건 통과.
- 운영 PC에 접근할 수 없어 운영 설치를 변경하지 않는다. 신규 worker의 복구 검사는 기존 0.4.42 worker에 소급 적용되지 않으며 문서에 제한을 기록했다.
- GitHub 반영은 별도 수정 브랜치/PR로 진행한다. 자동 업데이트 원본은 main이므로 병합 전에는 후보가 운영 배포되었다고 보고하지 않는다.
- 최종 전체 1,282개 통과, TypeScript·프로덕션 빌드·central:check·check·diff 검사 통과. 오류 제보 수집·전송 구현 파일은 수정하지 않았다.
