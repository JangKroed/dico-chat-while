# 0.4.42 중지·연결 해제·자동 복구

## 재현 원인
운영 기록에서 중지 CONTROL은 applied인데 execution_tab_changed 관찰이 같은 unknown 시도에 반복되며 그룹 상태를 needs_review로 덮어썼다. 입력 차단(executionBlocked=true)이 확인돼도 unknown 기록을 진행 중 실행과 동일하게 취급하여 연결 해제·업데이트가 막혔다. 자동 RECONCILE와 거절된 CONTROL 재발급에는 3회 상한이 남아 있었다.

## 변경
- 반복 미확인 관찰은 동일 사건을 다시 생성하지 않고 사용자의 stopped/paused 상태를 유지한다.
- 구버전에서 덮어쓴 중지 상태는 같은 runId/controlGeneration의 모든 멤버 stop ACK가 applied인 경우에만 복구한다.
- 중지/일시정지 적용 및 입력 차단을 확인한 미확인 시도는 detached 이력으로 보존하면서 연결을 해제한다. 결과는 unknown 그대로이며 성공·미발송으로 바꾸지 않는다. 실제 입력 가능성이 남아 있으면 해제를 거절한다.
- 분리 이력은 예약·복구·시작 제한에서 제외한다. 지연된 확장 보고는 삭제된 그룹이나 연결을 복원하지 않는다. 사용자 확인으로 확정하더라도 과거 재생 목록을 진행하지 않는다.
- 확장 CONTROL 적용은 로컬 unknown 결과에도 실행 차단 근거를 저장한다. CLOSE_CHANNEL은 이를 확인한 경우에만 과거 미확인 기록을 남기고 해당 탭을 정리한다. 기존 사용자 탭 보호는 유지한다.
- 미확인 조회는 횟수 상한 없이 5~30초 간격으로 계속한다. 중지 거절 복구와 시스템 재개도 횟수 상한을 제거하고 재개 오류 간격은 최대 30초로 제한한다.
- 현재 RECONCILE 명령의 확실한 성공 근거로 결과가 해결되면 이전에 실행 중이던 동일 run만 이어간다. 사용자 stop/pause, 비활성, 프로세스 재시작 의도는 우선하며 미확인 상태에서 재전송하지 않는다.
- 연결에서 분리된 차단 이력은 데이터를 보존한 채 업데이트를 진행할 수 있다.

## 전달 범위
같은 변경 묶음에 앞서 요청한 그룹 선택 실행/활성화, 로그인 확인 창의 서버별 탭 그룹, 발송·입력 준비 카운트다운 구분, 완료된 업데이트의 수동 처리 안내 제거를 포함한다.
운영 DB는 읽기 전용으로 진단했으며 사용자 Discord 발송/실행/연결 해제를 임의로 수행하지 않았다. 실제 Chrome UI 검사 및 운영 적용 결과는 별도 확인 전까지 미검증이다.

## 제출한 입력창 비움 완료 경로 수정

0.4.41 설치본과 후보 소스를 동일한 가상 DOM/시계에서 비교했다. 계정 패널만 재생성하고 실제 계정·채널·입력창은 유지한 조건에서 구버전은 sameEditor=true인데 sameComposer=false를 영구 기록했다. 원인은 proofMatchesPanel 실패를 실제 계정 변경과 동일하게 scopeChanged에 고정하는 식이었다. 이는 일시적인 증명 불가를 계정 변경의 증거로 잘못 취급했다.

- 정확한 초안 제출 후 입력창이 비었고 계정 패널 응답만 40초 유실되는 조건: 설치본 0.4.41은 Enter 뒤 25,000ms에 ACCOUNT_UNVERIFIED/uncertain, 후보는 Enter 뒤 0ms에 composer_cleared/confirmed.
- 첫 두 Enter를 가상으로 무시하고 재시도 중 패널만 교체한 조건: 설치본은 26,600ms 뒤 COMPOSER_EDITOR_CHANGED/uncertain, 후보는 2,700ms에 세 번째 Enter로 confirmed.

완료는 제출 전에 검증된 계정과 실제로 제출한 동일 입력창의 비움으로 판단한다. 이후 계정 패널 재조회 응답은 완료의 추가 대기 조건이 아니다. 실제 다른 계정 ID/채널 변경, 다른 입력창, 수동 초안 변경은 계속 구분한다. 계정 증명이 일시적으로 불가하고 입력창이 남은 경우에는 읽기 전용 관찰/상태 유지로 복구하며 새 Enter 전에 현재 계정을 다시 검사한다. 별도 채팅 DOM 조회나 500ms 비움 대기를 요구하지 않는다.

위 시간은 통제된 재현의 가상 시각이며 운영 PC에서 개선 시간을 실측한 값이 아니다. 운영 중단 기록의 sameEditor=true/sameComposer=false/accountMatched=false와 일치하는 결함을 수정했지만, 반복 Enter가 처음부터 받아들여지지 않는 모든 원인을 입증한 것은 아니다. 입력창이 실제로 비지 않는 경우의 재시도는 별도 문제로 남을 수 있다.

검증: 전체 1,269개 테스트, TypeScript/프로덕션 빌드 통과. 계정 패널 재생성, 입력창 비움 중 계정 조회 유실, 실제 다른 계정 변경 차단 회귀 테스트를 추가했다.
