# 자동 제보 전송 신뢰성 보강 (2026-11-03)

## 확인한 원인과 수정

- 자동 제보가 수동 보고서의 본문·이름 포함 설정을 상속했다. 자동 제보에는 본문·표시 이름 포함을 항상 끄고, 오류 문자열·상세·설명 등 임의 텍스트를 제거한다. 비밀 키 이름 필터만으로 놓칠 수 있는 오류 메시지 내부 쿠키·비밀번호·토큰도 자유 텍스트 제거로 차단한다. 상태 코드, 시간, 횟수, 식별자 및 허용된 관찰값은 남긴다. 수동 내보내기 동작은 유지한다.
- 보고서 저장과 대기열 색인 저장 사이에 프로세스가 종료되면 보고서만 남을 수 있었다. `pending-queue.json`에 보고서와 항목을 먼저 원자 저장하고, 재시작 시 동일 항목으로 복구한다. 동일 프로세스에서 쓰기 실패 후 다음 요청이 들어와도 먼저 미완료 저널을 복구한다. 기존 incidentId/reportId 중복 방지 정보도 보존한다.
- 타임아웃이 AbortController 신호에만 의존했다. 신호에 응답하지 않는 전송 또는 응답 스트림도 전송 대기를 끝내고 재시도 예정 상태로 기록한다. 뒤늦은 접수 응답은 실패 상태를 완료로 바꾸지 않는다. 접수 응답을 잃은 경우 기존 reportId로 재시도하여 수신 측 중복 제거를 유지한다.

- 지수 백오프만으로는 영구적인 연결 실패가 무한 반복되었다. 전체 시도 한도를 기본 8회(`maxAttempts`, 1~100회)로 제한하고, 초과하면 `failed` 및 `nextAttemptAt: null`로 보존한다. 정기 전송·강제 전송·재시작 모두 종료 상태를 존중한다. 강제 전송은 백오프 대기만 건너뛴다. 구형 파일의 누적 시도 횟수도 요청 전에 검사한다.

- 자동 전송 동의를 끄면 대기 중인 자동 제보는 강제 전송에서도 보류하고 진행 중 자동 요청은 즉시 중단한다. 수동 전송 허용이 유지되면 수동 보고서는 보낼 수 있다. 동의를 다시 켜면 남아 있는 시도 예산과 백오프 정책을 적용한다. 동의 철회 회귀 테스트 2개도 수정 전 실패를 확인했다.

## 검증

첫 수정의 결함 재현 테스트 3개와 후속 재시도·구형 개인정보 테스트 3개가 수정 전 실패함을 확인했다. 추가로 오프라인 실패 후 재시작·개인정보 제거·정상 접수, 끝나지 않는 응답 스트림과 늦은 접수 응답을 검증했다. 신규 테스트 10개, 보고서 기존 테스트 12개, 이메일 중계 모의 테스트 6개가 통과했다. 실제 이메일은 발송하지 않았다.

기존 HTTP 전송 테스트 중 9개는 실행 환경의 `listen EPERM 127.0.0.1` 제한으로 로컬 서버를 열지 못했다. 그 테스트의 실제 네트워크 동작까지 통과했다고 주장하지 않는다.

## 범위와 한계

디스크가 가득 차거나 읽을 수 없는 경우의 저장 성공을 보장하지 않는다. 저널은 정상 파일 쓰기 후 프로세스 종료 사이의 공백을 복구한다. 이미 상대 서버가 받은 요청은 취소할 수 없으므로 수신 서버의 reportId 중복 제거가 필요하다. 변경 전 저장되어 자동/수동 표식이 없어도 incidentId가 있는 보고서는 자동 제보로 간주하여 재전송 전에 최소화한다. 표식과 사건 식별자 모두 없는 구형 보고서의 생성 방식은 추론하지 않는다.
