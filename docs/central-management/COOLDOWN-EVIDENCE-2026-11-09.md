# 슬로우모드 판독 근거 구분

사용자가 제한받는 계정과 서버장 계정을 교체한 뒤 지연은 계정을 따라 Chrome으로 이동했다. 운영 기록에서는 첫 Enter 이후 약 52.6초 동안 POST가 없었고, 직전 POST와 다음 POST 간격은 약 120.1초였다. 이 현상의 내부 Discord 제한 조건은 아직 미확인이다.

## 확인된 코드 문제

표시를 찾지 못한 경우에도 기존 cooldownKnown은 true이며 cooldownMs는 0이다. 이 값만으로 제한 해제나 계정 면제를 입증할 수 없다. 기존 실행기는 cooldownKnown=false를 실행 차단에 사용하므로 표시 부재를 일괄 false로 바꾸면 서버장 계정도 대기하게 된다.

## 이번 변경

- countdown, absent, hidden, unreadable 근거를 별도 기록한다.
- 입력창 조회 범위 바깥의 카운트다운 후보 개수만 기록한다. DOM 원문과 메시지 본문을 추가 수집하지 않는다.
- 중앙 전달 필터가 근거와 개수를 보존한다.
- 비교 분석기는 표시 부재와 구형 기록의 0초를 제한 해제 대조 표본에서 제외한다.
- 실행 정책과 운영 설치본 교체는 이번 변경 범위에 포함하지 않았다.

## 검증과 남은 작업

실제 content.js 실행 테스트에서 근거 필드 누락으로 수정 전 실패를 확인했다. 수정 후 전체 1,359개 테스트가 통과했다. 확장 빌드가 성공했다. 실제 Discord에서 이 수정본의 운영 검증은 수행하지 않았다.

다음 운영 계측에서는 제한 계정의 absent와 cooldownOutsideScopeCount를 함께 확인해야 한다. 바깥 후보가 있으면 현재 입력창과의 소속 관계를 확인해 조회 범위를 수정한다. 후보가 없으면 실제 표시 구조와 계정별 제한 근거를 추가 확인한다. 약 120초 간격 자체를 서버 제한 확정값으로 저장하지 않는다.

## 카운트다운 판독 수정

동일 입력창 범위의 cooldownText 클래스도 카운트다운 후보로 읽도록 수정했다. 이 형태를 사용한 실제 content.js 모의 실행에서 기존 코드는 8초 잔여를 0초로 읽었다. 수정 후에는 제한 종료 이전 Enter 0회, 종료 뒤 Enter 1회, 재입력 0회로 같은 차례가 완료된다. 기존 slowModeCooldown 형태도 유지한다.

수정 후 전체 1,360개 테스트, 중앙 검사, 확장 빌드가 통과했다. 현재 사용자의 Discord DOM이 cooldownText 형태인지 직접 확인한 것은 아니므로, 이 수정이 운영 지연의 원인을 해소했다고 단정하지 않는다. 운영 빌드 적용 후 새 근거 필드와 실제 반복 발송을 대조해야 한다.

## 0.4.56 운영 회귀와 0.4.57 수정

0.4.56 설치 후 실제 준비 경로에서 COOLDOWN_UNVERIFIED가 반복됐다. cooldownText를 전용 타이머로 취급한 확대가 과도했다. 일반 안내 문구는 대기 시간 근거로 사용하지 않고, 대체 클래스에서 시간 토큰이 확인된 요소만 선택한다. 기존 전용 타이머의 해석 실패 차단은 유지한다. cooldownWrapper의 시간 표기도 지원한다. 안내 문구가 있어도 같은 차례를 완료하는 회귀 테스트를 추가했다.

## 0.4.57 운영 확인 (2026-11-09 KST)

중앙관리, Chrome·Brave 확장, 실제 발송 콘텐츠 버전 0.4.57을 확인했다. 콘텐츠 빌드 접두는 643d557cb5ce이다. 승인된 중지·업데이트 뒤 기존 활성 그룹 1만 재개했으며 그룹 2·3은 중지 상태다.

제한 계정의 11:26:14, 11:27:43, 11:29:43 발송에서 각각 Enter 1회와 HTTP 200을 확인했다. Enter부터 POST까지 각각 7ms, 6ms, 11ms였다. 준비 단계에서는 잔여 35초와 5초를 실제 countdown 근거로 읽었다. 기존 0초 미감지 및 반복 Enter와 달리 발송 허가 전에 대기하게 됐다.

이 관찰은 반복 Enter 해소의 단기 근거다. 제한 계정의 실제 POST 간격은 89.37초와 120.039초이며, 채널 설정 60초와의 차이 및 준비 중 카운트다운 변화 전체는 아직 설명되지 않았다. 설정 60초만으로 모든 대기가 불필요하다고 판단하지 않는다.

## 최소화 전송 창 대조와 0.4.58

같은 제한 계정·채널·설정에서 전송 창을 reveal한 뒤 POST 간격이 120.151초에서 69.508초, 69.452초로 감소했다. 두 차례 모두 Enter 1회였고 POST까지 6ms였다. 이는 계정 설정 60초와 반복 120초의 차이에 창 가시성이 영향을 미친다는 운영 근거다. 브라우저 내부 타이머를 직접 계측한 것은 아니므로 내부 메커니즘까지 확정하지 않는다.

준비 단계에서 DICO 소유 전용 창만 최소화를 해제하고 대상 탭을 활성화한다. 포커스는 요청하지 않는다. 사용자 직접 연결 탭이나 일반 탭이 섞인 창은 변경하지 않는다. 창 작업 뒤 중지·세션을 다시 확인한다. 화면이 완전히 가려지거나 사용자가 다른 탭을 선택하는 조건은 별도 한계다.
