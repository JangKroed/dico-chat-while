# 로그·실시간 현황·그래프·알림 기획

작성: 2026-10-30 KST · 상태: 설계 명세와 기본 기능 개발판. 전체 목표와 [실제 구현 범위](IMPLEMENTATION.md)를 구분한다.

## 1. 목표와 제공 범위

사용자가 텍스트 로그를 끝없이 읽지 않아도 현재 진행 상태, 멈춘 이유, 영향을 받는 작업과 다음 행동을 알 수 있게 한다. 상세한 원인 분석은 같은 사건의 로그와 발송 기록으로 연결한다.

초기 범위는 실시간 페이지 표시, 대시보드 그래프, 알림 센터, macOS·Windows의 로컬 OS 알림이다. 여기서 PC 푸시 알림은 설치된 관리 프로그램이 보내는 OS 알림을 의미한다. 브라우저 페이지를 닫아도 관리 프로그램과 알림 구성 요소가 실행 중이면 받을 수 있도록 설계한다. 브라우저 탭의 알림 API만 사용하는 구조는 피한다.

휴대폰 원격 푸시, Web Push 중계 서버, 이메일·텔레그램·Discord 외부 전송은 초기 범위에 포함하지 않는다. 다른 PC나 사용자에게 로그를 공유하지 않는다. OS 알림 권한·집중 모드·프로그램 종료 상태에 따라 실제 표시가 달라질 수 있으며 표시를 보장했다고 안내하지 않는다.

## 2. 기록을 네 가지로 구분

| 구분 | 목적 | 사용자 화면 |
| --- | --- | --- |
| 발송 기록 | 발송 의도·허가·Enter·게시 확인·결과를 추적 | 실행 기록, 계정별 타임라인 |
| 활동 기록 | 메시지 수정·적용, 그룹 편집·시작·중지, 수동 결과 판단 | 최근 활동, 변경 이력 |
| 운영 진단 | 연결, 버전, 대기 사유, 저장 오류, 복구 상태 | 진단 로그, 대상별 상세 |
| 문제·알림 | 조치할 문제를 하나의 사건으로 묶어 추적 | 상단 알림, 알림 센터, OS 알림 |

로그 레벨과 발송 결과는 다른 축이다. `ERROR`라고 모든 발송을 실패로 집계하지 않고, `INFO`라는 이유로 게시 성공으로 세지 않는다. `DEBUG`·`INFO`·`WARN`·`ERROR`·`CRITICAL`을 사용하며 상세 디버그 수집은 기본 끈다.

## 3. 구조화된 이벤트

각 이벤트는 증가하는 eventId, 중복 제거 키, 발생 종류·레벨, 중앙 수신 시각, 출처 관측 시각(있을 때), 세션, 그룹·연결·계정·채널 참조, 발송/명령 ID, 적용 구성·메시지 버전, 상태 전이, 원인 코드, 사용자용 설명, 가능한 행동을 갖는다.

사용자 설명 예시는 `계정 B의 게시 여부를 확인하지 못해 모집방 순환이 기다리고 있습니다`다. 상세에서는 허가 발급·Enter 관측·응답 유실 등 연결된 근거를 보여준다. 예외 문자열만 던져 놓지 않는다.

예정·허가·Enter·확인 시각과 중앙 수신 시각을 구분한다. 서로 다른 프로세스의 단조 시간을 직접 빼거나, Discord 게시 ID의 시각과 PC 시계를 빼서 네트워크 지연이라고 표시하지 않는다. 벽시계 변경이 있으면 시간 측정 불가/참고값으로 구분한다.

비밀번호, Discord 토큰·쿠키, 연결 키, UI 접속용 값은 수집하지 않는다. 메시지 본문은 기본 로그 목록과 OS 알림에서 제외하고, 발송 상세의 기존 스냅샷을 권한 있는 로컬 화면에서 조회한다. 진단 내보내기는 본문 제외가 기본이며 포함하려면 선택과 미리보기를 제공한다.

## 4. 바로 알려주는 화면 동작

- 중앙 서비스가 상태·이벤트를 저장한 뒤 같은 이벤트 흐름을 페이지와 알림 처리기에 보낸다.
- 정상 로컬 연결에서 저장 완료 후 화면 반영 2초 이내를 개발·시험 목표로 둔다. 상태 갱신이 늦으면 최근 수신 시각과 `갱신 지연`을 표시한다. 계정 연결 끊김 감지는 별도의 heartbeat 기준을 따른다.
- 모든 페이지 상단에는 서비스 상태, 미해결 문제 수, 알림 센터 버튼, 전체 중지를 둔다.
- 현재 페이지의 대상에 문제가 생기면 해당 행과 상세에 원인·행동을 표시한다. 그룹 문제를 다른 페이지에서도 놓치지 않도록 상단 센터에 함께 반영한다.
- 단순 저장 완료는 짧은 토스트로, 미확인 발송·저장 오류처럼 조치가 필요한 문제는 지속 배너/문제 목록으로 제공한다.
- 알림 클릭은 해당 그룹·계정·발송 상세로 이동한다. 이동 과정에서 자동 재전송·재개·미발송 확정을 수행하지 않는다.
- 사용자가 로그를 읽는 동안 새 이벤트가 들어오면 위치를 밀지 않고 `새 로그 N개`를 표시한다. 맨 아래에서 실시간 보기를 켠 경우에만 자동 스크롤한다.

알림 읽음 처리와 문제 해결은 다르다. 알림을 닫아도 `미해결` 상태와 그룹의 안전 정지는 유지한다. 해결 조건을 충족하면 해당 사건을 `해결됨`으로 바꾸고 회복 이벤트를 연결한다.

## 5. 대시보드 지표와 그래프

기본 기간은 오늘이며 최근 1시간·24시간·7일·직접 기간을 선택한다. 그룹·계정·채널·브라우저 필터를 모든 차트와 연결한다. 집계 기준·시간대·최종 갱신을 표시하고, 차트를 누르면 같은 필터의 원본 기록으로 이동한다.

| 표시 | 형태 | 파악할 내용 |
| --- | --- | --- |
| 게시 확인 건수 | 시간대별 막대 | 어느 시간에 얼마나 게시 확인됐는지; 자동/수동 확인 구분 |
| 발송 시도 결과 | 누적 막대 또는 수치표 | 선택 기간에 생성된 시도의 확인·미발송·취소·미확인·진행 중 분포 |
| 계정별 진행 | 계정별 타임라인 | A → B → C의 허가·Enter 관측·게시 확인과 대기 구간 |
| 지연 추이 | 점/선 그래프와 p50·p95 | 중앙 허가 지연과 같은 탭의 Enter→게시 확인 시간을 별도 측정 |
| 대기 원인 | 원인별 가로 막대 | 슬로우 모드, 다른 계정 차례, 연결 끊김, 결과 미확인 등 |
| 연결 상태 | 브라우저별 시간 띠 | 연결됨·갱신 지연·끊김·관측 불가 구간 |

초기 대시보드는 운영 그룹 목록을 유지하고 그 아래 게시 확인 막대·계정 타임라인을 우선 배치한다. 나머지는 `분석 보기` 또는 로그·분석 화면에서 제공한다. 그래프 때문에 현재 문제와 전체 중지 버튼을 아래로 밀지 않는다.

### 집계 정의

1. **게시 확인 건수:** 중앙에서 결과를 처음 확정한 시각이 기간 안에 있는 고유 발송 ID 수. Enter 시도나 완료 보고 재전송은 추가하지 않는다. 수동 게시 확인은 별도 색·텍스트로 표시한다.
2. **발송 시도 분포:** 기간 안에 생성된 고유 발송 시도를 현재 결과 하나로 분류한다. `게시 확인`·`확정 미발송`·`Enter 전 취소`·`미확인`·`진행 중`은 서로 배타적이다. 결과가 늦게 확정되면 같은 시도의 분류를 변경하며 새 시도로 더하지 않는다.
3. **확정 결과 중 게시 확인 비율:** 위 생성 시도 집합의 게시 확인 / (게시 확인 + 확정 미발송). 미확인·진행 중·Enter 전 취소는 분모에서 제외하고 제외 건수를 함께 보여준다. 수동 확인 포함 여부를 표시한다. 전체 성공률로 이름 붙이지 않는다.
4. **중앙 허가 지연:** 연결·준비·슬로우 모드·차례·최소 간격 조건이 모두 충족된 시점부터 실제 허가 발급까지의 단조 경과 시간. 의도된 간격·슬로우 모드 대기는 장애 지연에 포함하지 않는다.
5. **게시 확인 시간:** 같은 content script에서 관측한 Enter부터 게시 확인까지의 단조 경과 시간. 중앙 서비스의 확인 수신 지연과 합치지 않는다. 측정 근거가 없으면 값 없음으로 둔다.
6. **대기 원인 시간:** 그룹별 상태 구간을 기간 경계에 맞춰 자르고 그 시점의 실제 차단 원인 하나에 배정한다. 우선순위는 미확인 → 연결/계정 문제 → 슬로우 모드 → 계정별 주기 → 그룹 간격 → 다른 계정 차례다. 보조 조건은 상세에만 표시해 시간을 중복 합산하지 않는다. 관측이 끊긴 구간은 원인 미상으로 분리한다. 여러 그룹을 합하면 단위는 `그룹·초`이며 병렬 그룹 때문에 실제 경과 시간보다 커질 수 있다. 실제 서비스 중단 시간으로 표시하지 않는다. 브라우저 연결 구간과 그룹 대기 구간도 합산하지 않는다.

게시 확인 막대는 확인 시각, 시도 분포는 생성 시각을 사용하므로 같은 기간의 총합이 다를 수 있음을 도움말에 설명한다. 연결 끊김/관측 불가를 0초 지연·정상 상태로 채우지 않는다. 일부 데이터만 남은 기간은 `일부 기록 없음`으로 표시한다.

차트에는 색 외의 범례, 정확한 수치 툴팁, 키보드 조작과 표 보기 대안을 제공한다. 표본 0이면 `측정 없음`, p95 표본이 20개 미만이면 값과 함께 `표본 부족`을 표시한다. 원인 발생 횟수와 대기 시간 합계는 다른 지표로 전환할 수 있게 한다.

## 6. 로그·분석 페이지 `/logs`

상단에는 검색과 기간·레벨·분류·문제 상태·그룹·브라우저·계정·채널 필터, `실시간 보기` 토글, 새 로그 수, 내보내기를 둔다. URL에 필터를 보존하되 본문·인증값·진단 원문을 넣지 않는다.

기본 보기에는 `현재 문제`·`분석`·`전체 로그` 탭을 둔다. 현재 문제는 사건 단위로 묶고 영향 범위·발생 시각·최근 관측·해결 상태·다음 행동을 표시한다. 분석은 대시보드 지표의 상세 차트, 전체 로그는 시각·레벨·대상·짧은 설명·결과를 보여준다.

행 상세 서랍에는 관련 발송/명령·상태 전이·측정 근거·설정 버전·원인 코드를 표시하고 발송 기록으로 연결한다. `기술 상세 복사`는 비밀 제외·내용 미리보기를 거친다. 동일 발송의 로그를 한 타임라인으로 모아 볼 수 있다.

가상 스크롤 또는 페이지 단위 조회를 사용하고, 전체 DB를 브라우저로 내려받지 않는다. 전체 로그가 많아도 그룹 중지·문제 해결·메시지 편집 화면이 막히지 않게 한다.

## 7. 알림 우선순위와 기본 정책

| 사건 | 페이지·대시보드 | 기본 OS 알림 |
| --- | --- | --- |
| 미확인 발송으로 그룹 정지 | 즉시 지속 배너, 해당 발송으로 이동 | 켬 |
| 저장 실패·상태 손상으로 새 허가 차단 | 최상단 문제, 복구 안내 | 켬 |
| 계정 불일치·중복 실행·버전 불일치로 실행 차단 | 원인과 영향 그룹 표시 | 실행 중 작업에 영향이 있으면 켬 |
| 실행 중 연결이 끊김 | heartbeat 기준으로 문제 생성 | 영향받는 그룹이 있으면 켬 |
| 조건 충족 후 중앙 허가가 30초 이상 지연 | 경고와 실제 측정값 | 기본 끔, 사용자가 켤 수 있음 |
| 의도된 간격·슬로우 모드 대기 | 정상 대기와 남은 조건 표시 | 끔 |
| 정상 게시 확인·메시지 저장·수동 중지 | 최근 활동·필요한 토스트 | 끔 |
| 문제 해결·연결 회복 | 기존 문제를 해결됨으로 갱신 | 회복 알림 선택, 기본 끔 |

30초 지연 기준은 초기 제안이며 설정에서 조정한다. 경고가 발송 간격을 줄이거나 다음 계정으로 건너뛰게 하지 않는다. 사용자가 종료한 유휴 브라우저마다 오류 푸시를 보내지 않는다.

### 중복·빈도 제어

- 그룹/대상·원인별 incidentId로 첫 발생을 알리고 반복 관측은 같은 사건의 횟수와 마지막 시각만 갱신한다.
- 같은 사건을 여러 확장/중앙 탭이 각각 OS 알림으로 보내지 않는다. OS 알림 발송 주체는 관리 프로그램의 단일 처리기다.
- 기본은 사건당 최초 1회와 심각도 상승 때만 OS 알림. 반복 알림은 기본 끄고 사용자가 켠 경우 최소 5분 간격이다.
- 연결 끊김처럼 하나의 원인이 여러 그룹에 영향을 주면 원인 하나와 영향 그룹 수로 묶는다. 별도 조치가 필요한 개별 발송 미확인은 상세에서 유지한다.
- 연결 회복은 30초간 정상 상태가 유지됐을 때 안정 회복으로 판정한다. 그 전에 다시 끊기면 같은 사건을 갱신한다. 안정 회복 후 새 사건이 생겨도 같은 대상·근본 원인의 OS 알림은 기본 5분 재알림 유예를 적용한다. 모든 상태 전이는 페이지에 남기고 심각도가 올라가면 별도 알림을 허용한다. 이 초기 수치는 설정·시험으로 조정한다.
- 일시 음소거·방해 금지 시간대를 선택할 수 있다. 페이지의 미해결 문제는 계속 보이며 음소거가 해결을 뜻하지 않는다.

OS 알림 내용은 기본 `DICO · 확인할 문제 1건`과 원인 요약으로 제한하고 메시지 본문·실제 계정/서버 이름은 숨긴다. 이름 표시 여부는 사용자가 선택한다. 클릭하면 로컬 중앙 페이지의 해당 사건을 열고 재인증이 필요하면 그 절차를 먼저 거친다.

알림 요청에는 가능한 경우 incidentId 기반의 고정 OS 식별자를 사용해 재처리 시 기존 항목을 갱신한다. OS 요청 직후 프로세스가 종료돼 전달 여부가 불분명한 경우에는 알림이 정확히 한 번 표시됐다고 주장하지 않는다. 고정 식별자로 교체할 수 없는 어댑터는 불명확한 요청을 무조건 재전송하지 않고 전달 상태를 알 수 없음으로 기록한다. 페이지의 미해결 사건은 계속 보존한다.

## 8. 알림 설정과 튜토리얼

설정에는 OS 알림 켜기, 유형별 선택, 반복 간격, 방해 금지 시간, 내용 숨김, 회복 알림, 지연 기준, `테스트 알림`을 제공한다. 권한 요청은 설명과 사용자 행동 후 실행하고 거절해도 페이지 기능을 사용할 수 있다.

상태는 `사용 안 함`·`권한 필요`·`사용 가능`·`전송 오류`로 구분한다. OS에 알림 전달을 요청한 것과 실제 사용자 화면 표시/열람을 동일시하지 않는다. 테스트 알림은 Discord 메시지를 보내지 않는다.

튜토리얼 마지막에는 대시보드 상태 읽기, 로그 필터, 그래프에서 원본 기록 열기, 테스트 알림을 짧게 안내한다. OS 알림 허용은 설정 완료와 발송 시작의 필수 조건이 아니다.

## 9. 수집·저장·성능·장애

발송·설정 변경은 상태 트랜잭션과 이벤트/outbox를 함께 저장한다. 화면·알림·통계는 같은 eventId와 발송 ID를 기반으로 처리하고, 재연결 시 중복 전달을 제거한다. 늦은 결과는 해당 시도의 생성 시각 버킷에서 결과 분류를 바꾸고, 게시 확인 건수는 최초 게시 확인 확정 시각의 버킷에 한 번 반영한다. 완료 보고 재전송이나 나중 수정 시각으로 최초 확정 시각을 덮어쓰지 않는다.

raw 이벤트를 세는 방식으로 차트 수치를 만들지 않는다. 발송 결과 집계는 고유 시도의 최신 확정 상태를 기준으로 생성하며, 이벤트가 중복 수신돼도 수치가 늘지 않는다. 통계 집계의 최종 eventId와 기준 시각을 보여주고 지연됐으면 표시한다.

로그의 양 때문에 허가 저장·중지 명령이 밀리지 않게 핵심 상태 기록과 선택적 상세 수집을 구분한다. heartbeat는 모든 수신을 영구 로그로 남기지 않고 상태 전이와 연결 구간을 저장한다. 원시 디버그는 기본 끄고 켰을 때 기본 7일·용량 상한을 둔다. 일반 운영 기록의 기본 90일과 미확인/활성 상태 영구 보존 예외는 제품 기획서를 따른다.

저장할 수 없으면 새 허가를 중단하고 가능한 페이지/OS 경로로 저장 오류를 알린다. 저장되지 못한 임시 진단은 제한된 메모리 버퍼로 구분하고 영구 기록된 것처럼 표시하지 않는다. 서비스 자체가 죽으면 같은 서비스는 알림을 보낼 수 없으므로 실행 관리자/감시 구성 요소가 종료를 감지해 재시작·알림을 시도하도록 설계한다. 감시기까지 종료되거나 OS가 꺼진 동안에는 즉시 알림을 보장할 수 없다. 재실행 시 미확인 시도와 기록 공백을 먼저 안내한다.

로그 다운로드는 필터 범위와 포함 항목을 먼저 보여준다. JSON은 상세 진단, CSV는 표 분석에 제공하고 CSV 셀의 수식 실행을 방지한다. 실행 잠금·허가·중복 차단 이력은 로그 정리 메뉴로 지울 수 없다.

실행 관리자/감시기는 사용자 종료·계획된 업데이트·로그아웃의 종료 이유와 재시작 의도를 구분한다. 의도된 종료는 오류 알림과 장애 자동 재시작에서 제외한다. 비정상 종료 후 서비스를 재시작해도 발송을 자동 재개하지 않는다. 종료 이유를 확정할 수 없으면 `이전 종료 상태 확인 필요`로 표시하고 근거 없이 정상/장애를 단정하지 않는다.

## 10. 추가 인수 기준

1. 같은 사건·발송 이벤트를 중복 전달해도 그래프 수치와 OS 알림이 중복되지 않는다.
2. 허가·Enter·미확인·게시 확인을 서로 구분하고 확인되지 않은 발송을 성공으로 집계하지 않는다.
3. 미확인에서 게시 확인으로 바뀌면 같은 시도의 분류만 이동하며 수동/자동 확인 구분을 유지한다.
4. 자정·기간 경계·시간대/시계 변경·늦은 결과·기록 정리에도 집계 기준과 결측 표시가 일관된다.
5. 정상 대기, 사용자 중지, 실행에 영향 없는 유휴 연결 종료는 기본 OS 경고를 발생시키지 않는다.
6. 중앙 페이지가 여러 개 열려도 OS 알림은 한 번 발송된다. 읽음/음소거는 문제 상태·허가를 바꾸지 않는다.
7. 페이지를 닫고 OS 알림을 시험하며, 권한 거절·집중 모드·서비스/감시기 종료 상태를 각각 검증한다.
8. 그래프의 막대/구간에서 동일 필터의 원본 발송·진단 기록으로 이동하고 표로도 같은 값을 확인한다.
9. 정상 로컬 환경에서 이벤트 저장→페이지 표시 지연을 측정해 2초 목표를 검증한다. 대량 로그에서도 중지·허가 경로의 지연을 별도로 측정한다.
10. 기본 로그·OS 알림·내보내기에서 연결 키·토큰이 없고 본문 포함 여부가 사용자 선택과 일치한다.
11. 연결이 반복해서 끊겨도 안정 회복 기준·대상별 재알림 유예를 지키며 화면 상태 이력은 누락하지 않는다.
12. 사용자 종료·업데이트·로그아웃은 장애 알림/자동 재시작으로 오인하지 않는다. OS 알림 접수 직후 프로세스를 종료해 안정 식별자 재사용 또는 보수적 재전송 금지 정책을 검증한다. 실제 표시 정확히 1회를 시험 결과 없이 보장하지 않는다.

## 11. 개발 단계 반영

- 중앙 데이터·관찰 화면 단계: 구조화 이벤트, 상태 갱신, 알림 센터와 현재 문제 목록부터 제공.
- 중앙 실행 제어 단계: 발송 타임라인, 결과 분포·지연·대기 집계, 원본 기록 연결.
- 튜토리얼·출시 검증 단계: OS별 알림 어댑터·내용 숨김·빈도 제어·테스트 알림, 서비스 종료 관측 시험.
- 휴대폰 원격 푸시는 로컬 전용 범위를 바꾸므로 별도 후속 기획으로 둔다.
