# 0.4.31 중단 및 자동 복구

## 재현한 원인
- 중단 게이트는 닫혀도 CONTROL은 발송 작업의 응답이 돌아올 때까지 같은 실행 대기열에서 기다렸다. 화면 관찰에 직접 중단 신호가 없어 대기가 길어질 수 있었다.
- 오래된 세션이나 이미 처리된 중단을 입력 게이트 검사 전에 반영하면 현재 실행까지 차단할 수 있었다.
- CONFIG_SYNC 거절 후 같은 연결에서 최신 설정이 적용되어도 이를 알림 해결 근거로 사용하는 분기가 없었다.
- 복구는 게시 기록만 대조했고 content의 정확한 완료 영수증을 재조회하지 않았다. 중앙 코어도 동일 세션의 unknown 시도에 composer_cleared 결과를 적용하지 못했다.

## 중단 처리
1. 확장이 유효한 현재 세션의 CONTROL을 받으면 입력 게이트를 즉시 닫는다.
2. 해당 그룹/실행의 탭에 DICO_CANCEL_DELIVERY를 전달한다. 시도 ID와 세션이 일치하는 작업만 취소한다.
3. 관찰은 바로 반환하고, 승인·대기 후 입력 직전에 취소 상태를 검사한다. 초안은 보존한다.
4. 실제 작업이 반환된 뒤에만 기존 대기열의 CONTROL 적용 ACK를 보낸다. 취소 신호 전달만으로 중지 완료를 주장하지 않는다.
5. 명시적으로 거절된 CONTROL은 3초 간격으로 최대 3회 재발급한다. 첫 재시도는 다음 tick에서 가능하다. 이전 거절 명령은 superseded로 보존한다.

이미 Discord가 받은 Enter를 취소하는 기능은 아니다. Enter 이전 취소는 미발송, 이후 결과가 불명확한 취소는 unknown으로 구분한다. 연결이 끊기거나 브라우저가 멈춘 경우 즉시 적용 ACK를 보장할 수 없다.

## 자동 복구와 알림
- tick에서 기존 수동 재검사와 동일한 증거 규칙으로 알림을 자동 재검사한다.
- 설정 동기화는 현재 세션/연결/설정 버전의 실제 적용 ACK가 있어야 해결한다.
- 실행 종료가 확인된 unknown만 동일 세션의 현재 연결·탭에서 읽기 전용 RECONCILE을 최대 3회, 5초 간격으로 요청한다. 대기 중 명령은 중복 발급하지 않는다.
- content의 완료 영수증은 시도/세션/원문/시작 시각/계정/채널/현재 입력창과 유효기간을 검증한다. 빈 입력창만 보고 성공을 새로 만들지 않는다.
- 정확한 완료 근거가 있으면 결과와 관련 알림을 해결한다. 없으면 unknown과 초안을 보존한다. 자동 복구는 Enter를 재실행하지 않는다.
- 중단한 그룹은 자동 재시작하지 않는다. 복구된 결과를 근거 없이 미발송으로 바꾸거나 잠금을 해제하지 않는다.

## 코드 읽기
- content.js: activeOperation, DICO_CANCEL_DELIVERY, performDelivery, watchMessage
- central/extension/executor.js: handleCommand의 interrupt와 RECONCILE 분기
- central/core/index.js: recoverControl, recheckIncidents, tick의 recovery 요청, DELIVERY_RESULT

## 검증
중단 관찰 깨우기, 승인 대기 중 취소, 다른 시도 취소 무시, 과거 세션 및 중단 재전달, 중단 재시도 상한, 최신 설정 적용 후 알림 해결, 정확한 영수증 복구를 회귀 테스트로 검증한다. 실제 수신자의 브라우저 상태는 별도 확인 대상이다.
