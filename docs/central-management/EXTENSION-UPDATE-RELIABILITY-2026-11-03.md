# 확장 버전 불일치 자동 복구 점검 (2026-11-03)

## 확정된 배포 버전 원인

원격 배포 HEAD `8487a07`의 파일을 읽어 관리 프로그램 `central/package.json`은 **0.4.33**, 확장 `central/extension/manifest.json`은 **0.4.27**임을 확인했다. 기존 빌드 스크립트가 확장 manifest의 버전을 그대로 읽어 콘텐츠 버전까지 생성하므로 코드 업데이트와 reload가 성공해도 브라우저에 0.4.27로 표시될 수 있었다.

빌드 스크립트는 이제 관리 프로그램 package 버전을 단일 원본으로 사용하여 manifest와 콘텐츠 버전을 함께 갱신한다. 키·아이콘·권한 등 나머지 manifest 필드는 유지한다. 중앙 배포 검사도 두 버전이 다르면 실패하도록 하여 빌드 생략 시 재발을 차단한다.

## 확인한 흐름

관리 프로그램 업데이트 worker는 설치 폴더의 `central`과 `extension`을 모두 교체한다. 브라우저는 파일 교체만으로 로드 중인 서비스 워커를 바꾸지 않으므로 별도 `EXTENSION_STATUS` 검사와 `chrome.runtime.reload()`가 필요하다. 네이티브 호스트는 실제 확장 파일 해시를 검증하고, 브라우저 프로필에 등록된 배포 패키지 복사본도 신원·구조·심볼릭 링크 여부를 확인한 뒤 동기화한다. 개발 저장소나 신원을 확인할 수 없는 임의 폴더는 덮어쓰지 않는다.

기존 코드는 reload 직전에 저장한 대상 빌드 표식을 reload 호출 실패 후에도 유지했다. 다음 검사에서는 성공적으로 재시작했으나 다른 폴더를 로드한 경우로 오인하여 자동 복구를 영구 중단했다. 또한 실제 패키지 폴더를 호스트가 복구한 뒤에도 같은 표식이 재시작을 차단했다.

## 수정

- 실제 reload 호출 실패를 별도 상태로 저장한다. 30초 검사 간격을 유지하며 빌드당 최대 3회 자동 시도한다. 서비스 워커가 새로 만들어져도 실패 횟수는 유지한다.
- 실제 등록 패키지 동기화가 검증되어 호스트가 `repairedCopies > 0`을 반환한 경우에는 과거 잘못된 폴더에서 남은 재시작 표식에 한해 새 재시작을 허용한다. 파일 변경 없이 동일 빌드를 반복 reload하는 루프는 계속 차단한다.
- 중앙 확장 교체 승인에서 전체 앱 교체 정책을 분리한다. unknown 결과의 executionBlocked=true가 확인되고 그룹이 stopped/paused/needs_review이며 미완료 중지 제어가 없는 경우에만 확장 교체를 허용한다. 시도 결과·그룹 잠금·전체 앱 업데이트 차단은 변경하지 않는다. 준비/실행 중 시도는 계속 교체를 금지한다.
- 저장 실패나 reload 실패 시 로컬 maintenance를 해제한다. 발송 중 상태 또는 중앙의 reloadSafe=false를 무시하지 않는다.

## 검증과 관찰 한계

reload 복구 2개, 차단된 unknown의 확장 교체 허용 1개, 실제 빌드 버전 동기화·배포 검사 2개의 회귀가 수정 전 실패하고 수정 후 통과했다. 활성 발송 차단 회귀와 기존 확장 업데이트·패키지 폴더 동기화·네이티브 호출·관리 프로그램 업데이트를 포함한 관련 50개 테스트가 통과했다. 테스트는 임시 패키지와 가짜 Chrome API를 사용했으며 사용자의 실제 브라우저 폴더나 실행 중 설치를 변경하지 않았다.

0.4.33 배포 파일 자체의 버전 불일치는 확인했다. 다만 화면만으로 사용자의 실제 로드 폴더와 현재 로드된 코드 해시까지 확정할 수는 없다. 현재 실행 중인 구형 확장 코드는 새 파일이 설치되어도 reload되기 전에는 새 복구 로직을 실행하지 않는다. 중앙 reloadSafe와 로컬 maintenance의 미확인 발송 처리, heartbeat에서 업데이트 검사를 실행하는 순서도 함께 검증해야 한다.
