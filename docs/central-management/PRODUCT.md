# DICO 중앙관리 제품 기획서

## 1. 목표와 사용 환경

핵심 목표는 여러 브라우저에 흩어진 설정을 한곳으로 모아, 어떤 계정이 어느 채널에 어떤 메시지를 언제 보내는지 쉽게 설정하고 확인하는 것이다. 순서가 꼬이거나 결과가 불확실할 때 원인과 다음 행동을 표시한다.

사용 단위는 PC 한 대의 OS 사용자 한 명이다. 다른 사용자의 PC, 다른 OS 사용자 세션과 메시지·토큰·기록을 공유하지 않는다. 같은 PC의 여러 브라우저·프로필은 하나의 개인 작업 공간에 연결한다. 클라우드 로그인, 팀 권한, 원격 PC 제어, 여러 PC 동기화는 초기 범위에 포함하지 않는다.

Chrome·Brave의 일반 프로필을 우선 지원한다. 다른 Chromium 브라우저는 확장 설치 가능 여부와 네이티브 호스트 등록·연결·절전 후 복구를 검증해야 지원으로 표시한다. 시크릿 창, 게스트 프로필, 기업 정책으로 네이티브 통신이 차단된 환경은 초기 지원 범위에서 제외한다.

## 2. 성공 기준

- 일반 설정에 IP·포트·연결 토큰 입력란이 없다.
- 첫 설치 뒤 브라우저 연결, 메시지 작성, 채널 적용, 그룹 구성을 안내에 따라 완료할 수 있다.
- 모든 연결된 브라우저·계정·채널의 상태를 중앙 페이지에서 확인한다.
- 한 채널에 메시지 1개 또는 여러 개를 선택하고 적용 순서를 바꿀 수 있다.
- 계정 A → B → C 순서를 반복 실행해도 준비/통신 지연 때문에 다른 계정이 추월하지 않는다.
- 명령을 보내기만 한 상태와 확장에서 실제 적용한 상태를 구분한다.
- 불확실한 발송을 자동 재전송하거나 다음 계정으로 건너뛰지 않는다.
- 메시지 수정·적용·삭제가 발송 중인 문구를 바꾸지 않는다.
- 중앙 페이지를 닫아도 백그라운드 프로그램과 브라우저가 실행 중이면 작업이 유지된다.
- 브라우저·프로그램 재시작 후 연결과 데이터를 복구하되 사용자 확인 없이 발송을 재개하지 않는다.

## 3. 사용자가 다루는 개념

| 이름 | 의미 | 예시 |
| --- | --- | --- |
| 연결된 브라우저 | 확장이 설치된 브라우저 프로필의 연결 인스턴스 | 업무용 Chrome, 공지용 Brave |
| Discord 계정 | 해당 연결에서 확인한 로그인 사용자 | 계정 A |
| 연결 채널 | 브라우저·계정과 Discord 채널의 연결 | Chrome / A / 서버1의 모집방 |
| 보관 메시지 | 이름·태그·본문과 수정 이력을 갖는 재사용 문구 | 주말 모집 안내 |
| 채널 메시지 목록 | 해당 연결 채널에서 사용할 메시지와 순서 | 모집 안내 → 추가 공지 |
| 발송 그룹 | 같은 Discord 채널에 참여할 연결 채널과 계정 순서 | 모집방: A → B → C |
| 발송 시도 | 고정한 문구·계정·채널에 대한 1회 발송 의도와 결과 | 계정 B의 세 번째 공지 |

브라우저의 종류·표시 이름은 식별자가 아니다. 설치마다 고유 연결 ID를 발급하고 이름은 사용자가 바꾼다. 실제 브라우저 프로필 이름을 무조건 읽을 수 있다고 가정하지 않는다. 동일 Discord 계정이 여러 연결에 보이면 충돌 후보를 안내하고 해당 채널의 실행 담당 하나를 선택한다.

## 4. 최초 설정과 일상 사용

### 최초 설정

1. OS에 맞는 DICO 관리 프로그램 설치. 프로그램은 로컬 서비스를 시작하고 중앙 페이지를 연다.
2. 로그인 시 자동 실행 여부 선택. 재실행 시 같은 데이터 폴더와 서비스 인스턴스를 사용한다.
3. 브라우저별 확장 설치와 필요한 연결 권한 허용. 설치 완료는 연결 응답을 받은 뒤에만 체크한다.
4. 연결된 확장에 표시 이름 지정. 각 확장에서 로그인 계정과 대상 Discord 채널을 연결한다.
5. 메시지 보관함에서 문구를 작성한다. 처음부터 최소 한 개로 시작할 수 있다.
6. 연결 채널에서 메시지를 선택하고 순서를 지정한 뒤 적용한다.
7. 발송 그룹에서 계정 순서와 최소 간격을 정한다. 한 계정만 참여하는 그룹도 허용한다.
8. 실행 전 요약에서 계정·채널·문구·순서·최소 간격을 검토하고 시작한다.
9. 대시보드에서 첫 게시 확인과 다음 차례를 관찰한다. 튜토리얼은 설정 완료만으로 시험 메시지를 보내지 않는다.

각 단계의 완료 상태는 실제 저장·연결 상태에서 계산한다. 건너뛰었다면 미완료 목록을 남긴다. 튜토리얼은 중단 지점에서 이어가며 완료한 단계도 도움말에서 다시 볼 수 있다. 추가 브라우저 연결은 기존 설정을 다시 하는 대신 새 연결 안내만 연다.

### 일상 사용

프로그램 실행 → 대시보드의 연결 상태 확인 → 필요하면 보관 메시지 수정 및 채널 적용 → 작업 시작/재개 → 대시보드에서 관찰 → 중지 또는 일시정지. 문제 발생 시 해당 행에서 원인과 복구 행동을 확인한다.

## 5. 메시지 보관함과 적용 정책

| 동작 | 정책 |
| --- | --- |
| 작성 | 이름과 본문 필수, 태그 선택. 현재 발송기의 1~2,000자 검증과 전체·역할 멘션 제한 유지 |
| 수정본 저장 | 보관함의 새 수정 버전 생성. 채널에 자동으로 배포하지 않음 |
| 복제 | 별도 메시지 ID를 만들고 원본과 독립 편집 |
| 채널에 적용 | 대상 채널과 메시지 버전·순서 선택 → 영향 요약 → 적용. 기존 사용 채널 전체를 기본 선택하지 않음 |
| 여러 문구 선택 | 채널당 1~50개 메시지를 순서대로 반복. 한 개면 같은 문구 반복 |
| 반복 위치 | 해당 계정의 게시가 확인된 경우에만 다음 메시지로 이동 |
| 목록 변경 | 적용 시 현재 목록을 새 버전으로 저장하고 새 목록의 첫 문구부터 사용. 화면에서 이를 명시 |
| 준비/발송 중 변경 | 진행 중 발송은 고정 버전을 사용. 준비 전의 다음 발송부터 새 목록 적용 |
| 미확인 발송 중 변경 | 수정본 저장은 가능; 해당 채널 적용은 결과 확인 후 가능 |
| 삭제 | 사용 중이면 보관 처리 또는 채널에서 먼저 해제하도록 안내. 참조 중 문구를 즉시 영구 삭제하지 않음 |
| 보관 | 기존 적용본의 실행·조회는 유지하고 새 채널 선택에서 기본 숨김 |
| 영구 삭제 | 채널·대기 적용·미확인 발송에 참조되지 않은 항목만 허용. 실행 기록에 필요한 최소 스냅샷은 기록 보존 정책을 따름 |

수정본과 적용본의 차이를 채널 목록에 `새 수정본 있음`으로 표시한다. 발송 기록에는 당시 사용한 메시지 이름과 버전을 남긴다. 미리보기는 Markdown·이모지를 보조적으로 보여주며 Discord에서 보일 모양과 완전히 같다고 표시하지 않는다. 생성형 작성, 변수 치환, 예약 게시 기간, 첨부파일은 초기 범위에 포함하지 않는다.

메시지 목록 변경이 준비 중이라면 그룹을 `일시정지 요청` 상태로 두고 현재 시도 결과를 먼저 확정한다. 적용이 완료되기 전에는 새 구성으로 발송을 허가하지 않는다. 버전 충돌 시 나중 저장이 무조건 덮어쓰지 않고 최신본 다시 불러오기와 수정본 보존을 제공한다.

## 6. 채널과 발송 그룹

그룹 하나는 하나의 논리적 Discord 서버·채널을 대상으로 한다. 그 채널에 연결된 계정의 순서를 편집한다. 다른 Discord 채널은 다른 그룹으로 만들고 각각 진행한다. 계정 하나의 독립 반복도 같은 실행 엔진에서 1인 그룹으로 처리해 이중 타이머가 생기지 않게 한다.

채널 메시지 목록은 계정별로 다를 수 있다. 예를 들어 A가 문구 1·2, B가 문구 3, C가 문구 4·5를 선택하면 계정 차례는 A → B → C → A이고, A의 다음 차례에는 문구 2를 사용한다. 다른 사람의 수동 메시지까지 포함한 Discord 전체 채팅 순서를 통제하는 기능은 아니다.

### 시간과 순서

- 그룹 간격은 이전 게시 확인을 중앙에서 받은 뒤 다음 계정에 허가하기까지의 최소 시간이다.
- 계정·채널별 최소 주기와 Discord 슬로우 모드를 함께 지킨다.
- 다음 발송은 그룹 차례, 그룹 간격, 해당 계정의 대기, 연결·계정·채널 검증이 모두 충족돼야 한다.
- 대시보드의 예정 시각은 조건부 예상이다. 연결이 불확실하면 고정 시각 대신 대기 이유를 표시한다.
- 로컬 서비스가 예약을 소유한다. 브라우저 알람은 복구 보조로만 사용하며 독립 발송 타이머를 병행하지 않는다.
- 절전·브라우저 지연 뒤 누락 횟수만큼 몰아서 보내지 않는다.
- 같은 Discord 채널을 대상으로 하는 그룹은 동시에 실행하지 않는다. 동일 계정·채널에 대한 중복 실행도 거부한다.

그룹 편집은 정지 상태에서 한다. 실행 중 순서·계정 변경 요청은 먼저 일시정지·진행 시도 확정을 거친다. 빠진 계정을 자동으로 건너뛰거나 계정을 삭제해 미확인 허가를 없애지 않는다.

### 실행 제어

| 제어 | 사용자에게 약속하는 동작 |
| --- | --- |
| 시작 | 검증 후 다음 문구로 실행. 첫 발송은 조건 충족 시 즉시 가능하므로 실행 전 요약에 안내 |
| 일시정지 | 새 허가를 막고 현재 시도 결과를 확정한 뒤 계정·문구 차례 보존 |
| 재개 | 같은 차례에서 시작. 기존 대기·미확인 상태를 무시하지 않음 |
| 중지 | 예약 실행 의도를 종료. 차례·메시지 선택·기록 보존. 차례 초기화는 별도 명시적 동작 |
| 전체 중지 | 모든 새 허가 중단. 확장별 적용 응답과 남은 진행·미확인 발송 수 표시 |
| 확장 긴급 중지 | 해당 연결의 새 전송을 즉시 차단하고 중앙에 알림. 그룹 차례는 추월시키지 않음 |

Enter가 이미 전달된 메시지를 취소했다고 표시하지 않는다. 연결 끊긴 확장에는 `중지 확인 대기`를 표시하고, 결과가 확정되기 전에는 안전하게 중지 완료했다고 주장하지 않는다.

## 7. 장애·재시작·복구

| 상황 | 동작과 안내 |
| --- | --- |
| 브라우저 닫힘 | 연결 끊김, 담당 계정과 영향받는 그룹 표시. 다른 계정이 추월하지 않음 |
| 관리 프로그램 종료 | 새로운 중앙 허가가 없어 발송 정지. 진행 중 시도는 재시작 때 게시 확인부터 수행 |
| OS 절전/재부팅 | 연결 복구 후 재개 필요. 지난 예약 몰아보내기 금지 |
| 허가/발송 응답 유실 | 발송 시도와 허가 보존, 해당 그룹 `확인 필요`. 자동 재발송 금지 |
| 게시 확인 후 완료 보고 유실 | 실제 재발송 없이 같은 완료 보고만 재시도. 차례는 한 번만 이동 |
| 미발송 수동 확인 | 지연된 발송 가능성을 해소한 뒤 허가 종료. 계정·문구 차례 유지 |
| 다른 계정으로 로그인 | 계정 불일치로 시작/발송 차단, 다시 연결 안내 |
| 계정 확인 불가 | `계정 확인 필요`. 기본 아바타 등에서 현재 검증 제한을 우회하지 않음 |
| 저장 실패/손상 | 새 허가 발급 중단, 복구 화면 제공. 임의 초기화 금지 |
| 버전 불일치 | 해당 확장을 업데이트/새로고침하기 전 실행 차단 |

미발송 수동 확인은 이전 전송용 탭/진행 요청이 더 이상 Enter를 수행할 수 없는 상태를 확인한 후 제공한다. 단순 타임아웃이나 사용자의 버튼 클릭을 발송 취소 증거로 사용하지 않는다. 확인 불가능하면 미확인 상태를 유지한다.

## 8. 데이터와 사용자 설정

전체 데이터는 사용자 로컬 저장소에 보관하고 앱 업데이트와 분리한다. 작업 공간은 OS 사용자별로 하나다. 중앙 페이지에 별도 온라인 계정 가입을 요구하지 않는다. 같은 OS 사용자 권한으로 실행되는 다른 프로그램까지 격리하는 보안 경계는 제공하지 않는다.

백업에는 메시지·태그·적용 목록·그룹 설정을 포함하고 브라우저 인증정보·연결 키·활성 허가는 제외한다. 복원 전 현재 진행 중 시도를 확정해야 한다. 복원 결과는 항상 정지 상태이며 브라우저·계정·채널 재연결 후 시작할 수 있다. 백업으로 미확인 발송을 없애는 경로를 만들지 않는다.

설정은 로그인 시 자동 실행, 대시보드 열기, 시스템 알림, 기록 보존 기간, 백업·복원, 업데이트, 브라우저 연결 해제, 데이터 폴더 열기를 제공한다. 알림 권한 거절이 발송을 막지는 않는다. 업데이트는 모든 연결의 실행·준비·미확인 여부를 확인하고 작업 종료 후 적용한다.

실행 기록의 기본 보존은 90일로 제안하고 30/90/180일·직접 삭제를 선택하게 한다. 보존 기간 정리는 완료·확정적 미발송 등 종료된 기록에만 적용한다. 활성 허가, 미확인 시도, 미적용 명령, 현재 적용 메시지와 참조 중 버전은 기간과 관계없이 보존한다. 오래된 기록을 정리해도 같은 발송 ID를 재실행하지 않도록 필요한 중복 차단 식별 이력은 유지한다. 메시지 본문이 포함된 백업과 진단을 내보낼 때 포함 범위를 안내한다.

## 9. 초기 출시 인수 기준

1. macOS·Windows 각각 Chrome과 Brave를 연결하고 수동 IP·토큰 입력 없이 재연결된다.
2. 같은 브라우저의 서로 다른 프로필을 각각 구분하고 사용자가 이름을 붙일 수 있다.
3. 3계정 순환 100회에서 지연·중복 명령을 주입해도 관리 대상 계정의 순서가 바뀌지 않는다.
4. 메시지 1개·여러 개 적용, 순서 변경, 준비 중 수정, 보관/삭제가 규칙대로 동작한다.
5. 여러 중앙 페이지에서 수정해도 버전 충돌을 알려주고 기존 편집 내용을 보존한다.
6. 중지 명령 응답 유실·브라우저 종료·서비스 강제 종료 후 허위 완료나 자동 재발송이 없다.
7. 재설치/업데이트가 메시지와 미확인 발송 정보를 삭제하지 않는다.
8. 기존 A/B 설정을 미리보기 후 가져오고 다음 문구 차례를 보존한다.
9. 실제 게시 결과와 예정/시도/확인 시각을 구분한다. UI 상태가 오래됐을 때 즉시 알 수 있다.
10. 깨끗한 사용자 환경에서 Node.js 별도 설치 없이 설치·제거·재설치를 검증한다.

화면·자동화 테스트는 가상 Discord 화면을 사용한다. 실제 계정 발송은 사용자가 별도로 승인한 채널·문구·횟수로 수행하는 출시 검증 항목이다. 이 기획 문서는 실제 발송을 실행하라는 지시가 아니다.

## 10. 로그·실시간 현황·알림 추가 요구

[로그·그래프·알림 명세](OBSERVABILITY.md)를 제품 요구와 인수 기준에 포함한다. 실행 기록과 별도로 로그·분석 화면과 상단 알림 센터를 제공하고, 발송 건수·결과·계정별 순서·지연·대기 원인·연결 상태를 그래프로 볼 수 있게 한다. 그래프는 필터와 원본 기록으로 연결한다.

실시간 화면과 OS 알림은 같은 사건을 기준으로 만들며 읽음/닫기/음소거와 문제 해결을 구분한다. 정상 발송과 의도된 대기는 기본 OS 알림을 보내지 않는다. 미확인 발송·저장 오류·실행에 영향을 주는 연결 끊김 등 필요한 문제만 기본 알림 대상으로 제안한다. 초기 푸시 범위는 PC의 로컬 OS 알림이며 휴대폰 원격 알림은 별도 기획이다.
