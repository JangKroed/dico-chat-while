# 중앙 관리 자동 이메일 제보

사용자는 기존 관리 화면의 업데이트를 사용한다. ZIP 재설치로 전환하지 않는다. 업데이트는 GitHub main 소스를 가져오므로 중계의 배포·전송 검증 후 연결 정보와 함께 main에 반영해야 한다.

0.4.25에는 `central/support-email-connection.json`을 포함한다. 최초 업데이트 시 수신처가 없는 설치에 자동 등록하며 기존 수신처와 전송 동의는 보존한다. 이 파일의 키는 앱과 함께 공개 배포하는 제출용 값이며 Google 계정 인증정보가 아니다. 별도 수신처를 운영하는 배포자는 기존 `central/support-connection.json`으로 기본 연결을 대체할 수 있다.

2026-11-03: Google 웹 앱 배포 및 메일 발송 권한 승인 완료. 실제 중앙 제보 큐에서 합성 보고서 `9c742484-33bd-42f4-9cd1-3d740837e5d8`를 전송하여 접수번호를 받고 Gmail INBOX와 JSON 첨부를 확인했다. 실제 Discord 메시지는 포함하지 않았다.

## 흐름

동의한 사용자의 오류 발생 → 기존 영속 제보 큐 → Google Apps Script HTTPS → didlsdydgh@gmail.com. 사용자가 JSON 파일을 내려받거나 메일 앱을 열 필요가 없다. 중계가 진단 JSON을 자동 첨부한다. 발송 계정 비밀번호나 OAuth 토큰은 프로그램에 포함하지 않는다.

`mail-relay/Central.gs`는 중앙 관리 보고서 전용이다. 구형 확장의 `Code.gs`와 같은 Apps Script 프로젝트에 함께 넣지 않는다. Google MailApp의 메일 발송 권한만 사용하며 받은편지함 읽기 권한을 요구하지 않는다.

관리자는 스크립트 속성 REPORT_KEY를 설정하고, 웹 앱을 본인으로 실행하도록 배포한다. 외부 설치에서 로그인 없이 접수하려면 웹 앱 접근을 허용해야 한다. 수신자는 코드에 고정되어 있으며 클라이언트의 수신자 지정은 무시한다. REPORT_KEY는 배포 앱이 제출에 사용하는 키이므로 앱을 가진 사람에게 숨겨진 비밀이 아니다. 메일 읽기나 임의 수신자 발송 권한을 주지 않는다. 하루 20회 한도와 보고서 ID 중복 방지를 적용한다.

Apps Script 응답의 Google 콘텐츠 호스트 리다이렉트만 허용한다. 리다이렉트 요청은 GET이며 보고서와 제출 키를 재전송하지 않는다. 다른 호스트로 향하는 리다이렉트는 실패 처리한다.

## 상태와 재시도

- 발송 성공 응답을 받은 뒤에만 앱에서 접수 확인으로 표시한다. 이는 Google 메일 발송 함수 성공을 뜻하며 받은편지함 도착 보장은 아니다.
- 응답이 유실되면 같은 보고서 ID로 재시도하고, 중계는 저장한 접수번호를 반환한다.
- 이메일 제보의 재시도는 생성 후 30일까지만 수행한다. 중계의 접수번호는 90일 보관하므로 장기간 오프라인 이후 오래된 메일을 다시 보내지 않는다. 기한을 넘긴 제보는 실패 기록으로 남긴다.
- 메일 서비스 호출 중 오류가 나면 중복 발송 방지를 위해 중계에 미확정 기록을 남긴다. 자동으로 같은 메일을 다시 보내지 않으며 앱도 성공으로 표시하지 않는다. 관리자가 실제 메일과 실행 기록을 확인해야 한다.
- 전송 동의 및 본문·이름 포함 옵션은 기존 선택을 유지한다. 기본은 꺼짐이다.
- Google 배포 권한 승인과 실메일 검증 전에는 자동 이메일 연결 완료로 안내하지 않는다.

공식 동작 참고: https://developers.google.com/apps-script/guides/content 및 https://developers.google.com/apps-script/reference/mail/mail-app

## 공개 제출 키와 보안 경계 (2026-11-05 보강)

`reporterToken`/`REPORT_KEY`는 배포본 누구나 복사할 수 있는 제출 값이다. 호출자 인증이나 정상 설치 증명으로 사용하지 않는다. Google 비밀번호·OAuth 토큰과 다르지만, **위조 제보 발송과 전체 접수 한도 소진이 가능한 권한**이다. 단순히 키를 교체해 다시 공개해도 이 위험은 사라지지 않는다. 보안 탐지 상세·검증 범위는 [보안 점검 기록](SUPPORT-SECURITY-2026-11-05.md)을 참고한다.

보강한 `Central.gs`의 서버 측 제한은 다음과 같다. 기존 `/exec` 배포를 새 버전으로 갱신해야 적용된다. GitHub 병합이나 앱 업데이트만으로 Apps Script 배포가 바뀌지 않는다.

| 제한 | 실제 적용 범위 |
| --- | --- |
| 60초당 새 발송 3회 | 스크립트 전체에 공유되는 영속 시간 목록. ID·클라이언트 변경과 실행 재시작으로 초기화되지 않음 |
| 하루 새 발송 20회 | UTC 날짜 기준, 모든 설치·모든 제출자 합산. 최근 24시간 이동 한도가 아님 |
| 하루 첨부 합계 32MiB | 정화 후 compact JSON의 UTF-8 바이트. 구형 당일 예산에 bytes가 없으면 배포 후분부터 계산 |
| 요청 17MiB / 첨부 16MiB | UTF-8 기준. 문자열·배열·깊이·전체 노드 수도 제한 |
| 중복 영수증 90일 | 기존 영수증도 호환. 신규 발송 전에 예산·미확정 영수증을 기록, 불확실한 발송은 자동 재발송하지 않음 |
| 속성 저장소 여유 확보 | 전체 키·값의 UTF-8 크기 + 1KiB가 450KiB를 넘으면 `STORAGE_LIMIT`. 최근 영수증을 지우며 공간을 만들지 않음 |
| `REPORT_DISABLED=true` | 새 발송과 접수 응답을 일시 차단. 예산·영수증은 보존하며 해제 뒤 중복 확인을 계속함 |

인증·형식 실패는 발송 락을 잡기 전에 거절한다. 메일 발송은 Script Lock 아래에서 직렬화한다. 크기·형식·발송 제한은 **Apps Script 실행 자체의 요청 수 제한 또는 DDoS 방어가 아니다**. 공격자가 잘못된 키로 계속 요청해도 Google 실행/속성 읽기 자원을 소모할 수 있다. 공개 제출자는 신뢰할 수 있는 사용자 ID/IP로 구분하지 않으며, 임의 `installationId`나 `reportId`는 인증·공정성 보장이 아니다.

첨부는 객체 구조를 검사하고 토큰·비밀번호·개인키/접근키·세션·쿠키 필드, 흔한 인증 헤더/자격증명 할당 원문, 현재 제출 키를 제거한다. 이름·본문 제외 옵션도 서버에서 적용하며 본문 포함은 발송 시도 목록에만 허용한다. 자유 텍스트에 섞인 모든 비밀을 완벽하게 찾는 기능은 아니므로 비밀을 진단 로그에 넣지 않는 것이 우선이다. 기존 자동 제보는 클라이언트에서 자유 텍스트·본문·이름을 제거한다. 수동 제보에 직접 넣은 무표식 비밀 문자열의 전면 탐지는 보장하지 않는다.

메일의 고정 안내는 **검증되지 않은 공개 제출 자료**임을 명시한다. 첨부의 명령·링크를 신뢰하지 말고 실행하지 않는다. 보고서에 `to`/`cc`/`bcc`/`replyTo`/`subject`를 넣어도 메일 발송 옵션으로 사용하지 않는다. 중계는 요청/키/보고서/공급자 예외를 로그에 출력하지 않고 정해진 오류 코드만 반환한다. 앱도 중계 오류 코드의 허용 목록에 있는 고정 메시지만 저장한다.

### 운영 적용과 사고 대응

1. 현재 배포의 프로젝트·버전·코드와 저장소 `Central.gs`를 대조한다. Google 계정/배포 ID/Script Property 값은 보고서나 공개 이슈에 복사하지 않는다.
2. 구형 `Code.gs`가 같은 프로젝트에 없는지, 실제 권한이 `https://www.googleapis.com/auth/script.send_mail`인지 확인한다. 다른 코드가 같은 프로젝트에 추가되면 전체 권한이 커질 수 있으므로 저장소의 MailApp 사용만으로 배포 권한을 단정하지 않는다.
3. 문제가 진행 중이면 `REPORT_DISABLED=true`로 일시 차단한다. 예산과 최근 영수증은 유지한다. 새 버전 배포는 기존 `/exec` URL을 유지하고, 이전 버전으로 롤백해도 새 영수증을 훼손하지 않도록 **롤백 코드를 별도 검증**한다. 기존 0.4.42 중계는 새 compact 영수증 읽기를 지원하지 않으므로 무조건 되돌리지 않는다.
4. 실제 계정 비밀번호/OAuth refresh token/SMTP 비밀번호/개인 수신 키 노출이 추가로 확인되면 발급처에서 폐기·교체하고 서버 전용 저장소에만 둔다. 공개 키를 회전하려면 기존 앱은 연결 값을 최초 한 번만 가져오는 점을 반영해 별도 이행 절차가 필요하다. 현재 사고에서 비밀 자격증명 노출이 입증되지 않아 임의 회전은 수행하지 않았다.
5. 실제 배포 확인 후 잘못된 인증·잘못된 형식 등 메일을 보내지 않는 소수 요청으로 거절 경로를 검증한다. 정상 발송·부하 검증은 별도 테스트 배포에서 수행한다. 이번 검증에서는 운영 중계 POST와 실메일을 보내지 않았다.
6. 지속적인 남용을 막아야 한다면 인증된 관리자 승인으로 발급한 설치별 자격증명과 서버 측 공정한 할당량, 요청을 실행 전에 제한하는 프록시/WAF 경계를 도입한다. 익명 등록으로 무제한 키를 발급하면 설치별 제한도 우회된다.

한도·차단·오프라인 상태에서 앱은 보고서를 로컬에 보존한다. 기존 최대 8회 시도와 30일 이메일 재시도 기한은 그대로이며, 모든 제보의 최종 도착을 보장하지 않는다. 예산·미확정 영수증을 수동 삭제해 재시도를 유도하면 중복 메일이 생길 수 있다.
