# 정상 미발송의 계속 시도와 실제 오류 복구 분리

최신 요구를 반영해 사용자가 재시도 횟수를 선택하는 설정을 제거했다. 이전 `CORE-INTEGRITY-2026-11-03.md`의 ‘유한 재시도’ 절은 이전 요구의 검증 이력이며 현재 정상 미발송 정책에는 적용하지 않는다.

## 현재 정책

| 상황 | 처리 |
| --- | --- |
| 같은 실행에서 정상 미발송이 확인되고 실행기·중앙의 상태 검사를 통과함 | 횟수 상한 없이 같은 시도·같은 문구에서 계속 진행 |
| 사용자가 중지 또는 일시정지함 | 이후 Enter 허가와 진행 요청 차단 |
| 발송 결과가 불확실함 | `unknown` 유지, 자동 재전송 금지, 순서·자원 잠금 보존 |
| 허가 전 입력 준비의 일시적인 실제 오류 | 최초 실행 이후 최대 3회 복구, 소진하면 일시정지하고 오류 원인 기록 |
| 허가 전 초안 불일치 등 재시도하면 안 되는 실제 오류 | 복구 반복 없이 즉시 일시정지 |
| 세션·실행·설정 불일치, 진행 중단, 실제 발송 오류 | 기존 검증과 오류 경로 유지; 횟수 제거로 통과시키지 않음 |

`central/extension/retry-policy.js`는 정상 계속 시도용 내부 `normalizeSendRetries() => null`과 실제 준비 오류용 `DEFAULT_PREPARE_RETRIES = 3`을 분리한다. 내부 `null`은 무조건 재전송하라는 허가가 아니다. 전송 실행기는 매번 같은 초안·대상·계정의 안전한 미발송 상태를 확인하며 중앙의 세션, 실행 ID, 활성 시도, 설정, 연속된 재시도 번호, 중지 상태 확인을 통과해야 한다.

## 설정과 기존 데이터

- 새 설정·스냅샷·백업에 `maxSendRetries` 사용자 옵션이 없다.
- 구버전 UI가 보내는 설정이나 과거 백업의 `0`, `3`, `10`, `null` 등은 호환 입력으로 무시하며 옵션을 다시 만들지 않는다.
- 새 시도와 확장으로 전달되는 명령은 내부 계속 시도 정책 `null`을 사용한다.
- 기존 DB의 활성 시도에 남은 숫자 상한도 내부 계속 시도 정책으로 이행한다. 이전 누적 횟수, 실제 결과, 허가 이력과 잠금은 유지한다.
- 재시작은 이전 세션을 차단하는 기존 절차를 그대로 따른다. 과거 불확실 시도를 이행 때문에 다시 보내지 않는다.
- 완료된 과거 진단의 숫자 횟수는 역사적 근거이므로 수정하지 않는다.

## 재현과 검증

변경 전에 다음 회귀 실패를 확인했다.

1. 제거되어야 할 설정에 `maxSendRetries`가 남아 있었다.
2. 새 시도에 내부 계속 정책 `null` 대신 숫자 `3`이 전달됐다.

변경 후 다음을 검증했다.

- 정상 진행이 이전 최대값 10회를 넘어 12회까지 같은 시도·문구 순서를 유지한다.
- 사용자 중지 직후 13번째 진행과 기존 Enter 허가가 모두 거절된다.
- 재시도 번호 건너뛰기, 잘못된 실행 ID·설정, 중지된 실행 요청은 계속 거절된다.
- 오래 대기하는 Discord 제한은 정상 진행 관측이 유지될 때 같은 차례를 보존한다.
- 실제 입력 준비 시간초과는 최초+복구3회 뒤 일시정지하고 최종 오류를 남긴다. 횟수 옵션 제거가 실제 오류를 무한 반복하게 만들지 않는다.
- 허가 후 준비 거절은 결과 불확실로 보존하고 자동 재전송하지 않는다.
- 과거 상한 0인 활성 시도를 이행해도 기존 누적8회, `unknown`, 잠금이 유지되고 재개가 거절된다.
- 설정 API·백업·DB의 과거 횟수 값이 사용자 옵션을 복원하지 않는다.
