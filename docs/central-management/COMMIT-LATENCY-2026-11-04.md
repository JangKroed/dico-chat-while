# 준비 완료 이후 발송 지연 조사 — 0.4.39

## 확인된 실행 경로

PREPARE는 본문 붙여넣기와 1초 안정 검사를 끝낸다. 발송 가능 시각에 중앙이 COMMIT_PERMIT을 발급하고 실행기가 실행 상태를 저장한 뒤 content의 commit을 호출한다. 기존 commit은 처음 중앙·계정 승인을 요청하고, 쿨다운 및 500ms 입력 안정 검사를 수행한 다음 중앙·계정 승인을 다시 요청했다. 첫 승인은 실제 Enter에 사용되지 않아 정상 발송에도 통신 왕복 한 번이 불필요하게 추가됐다.

또한 requestDeliveryPermission이 일시 거절을 재시도하여 새로운 승인을 받아도 호출자에서는 최초 요청부터 백오프까지의 총시간을 2초 유효기간과 비교했다. 여러 번 대기한 후 200ms 만에 받은 유효한 승인도 만료로 판단해 안정 검사와 승인을 한 번 더 수행했다.

이는 기존 영상의 개별 지연 시간을 모두 설명한다는 의미가 아니다. 최신 코드에서 각각 재현한 독립적인 결함이며 영상 수신자 PC의 수정 후 실측은 아직 없다.

## 수정

- commit 진입의 중복 승인을 없애고 실제 Enter 직전 최종 승인을 유지한다. PREPARE 및 단독 발송의 본문 변경 전 승인은 유지한다.
- 성공한 개별 요청의 페이지 wall/monotonic 시작 시각을 반환하여 응답 지연을 계산한다. 외부 승인 시각 authorizedAt을 갱신하거나 2초 유효기간을 늘리지 않는다.
- 최종 승인 요청·응답도 진단 trace에 기록하여 승인 구간과 안정 검사 구간을 구분한다. 메시지 본문과 인증 정보는 추가하지 않는다.
- 최종 승인 이후 계정·채널·입력창·문구·조합 입력·포커스·쿨다운과 중단 신호를 다시 검사한다. 불명확한 발송을 재전송하거나 일찍 발송하도록 변경하지 않는다.

## 재현 테스트

실제 content 소스를 VM에서 실행하고 Discord DOM 및 확장 통신을 시험 환경으로 대체했다.

1. 승인 왕복을 750ms로 설정한 준비 완료 초안: 기존 승인 2회로 테스트 실패 → 수정 후 1회. commit 호출부터 Enter까지 2,000ms에서 1,250ms로 감소한다. 이는 합성 조건의 측정값이다.
2. 일시 거절 2회·각 1,500ms 백오프 뒤 200ms 승인 응답: 기존 4번째 승인까지 요청하여 실패 → 수정 후 세 번째 유효 승인으로 제출한다.
3. 늦은 승인, 승인 중 쿨다운 변경, 중지, 계정·초안 변경, 복구 중 취소 및 중복 제출 방지 테스트는 유지한다. 기존 시험의 고장 주입 위치를 '두 번째 commit 승인'에서 '첫 최종 승인'으로 옮겨 같은 실패 조건을 계속 검증한다. 단순히 실패 검증을 제거하지 않는다.

## 남는 시간과 검증 한계

최종 500ms 입력 안정 검사, 계정 확인 및 중앙 승인 통신은 남아 있다. 이전 입력 준비 시간이 아니라 준비 이후 중복 처리와 잘못된 승인 만료를 제거한 변경이다. 따라서 네트워크·브라우저 지연을 포함해 무조건 즉시 또는 정확한 예약 시각에 발송한다고 보장하지 않는다. 실제 사용자 계정으로 메시지를 시험 발송하지 않았다.

## 최종 검증

- 전체 테스트 1,213개 통과, 실패·건너뜀 0개.
- 중앙 UI 컴파일·사전 빌드 검증·확장 빌드·문법/CSP/manifest 검사·SSR 검사 통과.
- 실제 Chrome UI의 중지 조작·메시지 편집·진단 모드·롤백 요청 및 1440/1000/390px 화면 검증 통과. 콘솔 오류 없음.
- 별도 비교 실행에서 0.4.38의 실제 content 소스는 승인 2회·2,000ms, 수정 소스는 1회·1,250ms를 확인했다. 합성 승인 지연은 두 실행 모두 750ms였다.
- 발송 관련 회귀는 VM의 실제 content 소스와 모의 Discord 환경에서 실행했다. UI 브라우저 검증과 실제 Discord 발송 검증은 구분한다.
