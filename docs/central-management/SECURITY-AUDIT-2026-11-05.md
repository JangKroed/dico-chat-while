## 판단과 범위

조사 기준은 `main`의 `cf18098`(0.4.42), 도입 커밋은 `66f7df42aa8440786291caca83f28251f1c0ab46`이다. GitGuardian 알림은 2026-11-03 13:57 KST의 Generic High Entropy Secret 탐지이며, 이메일 자체는 해당 값의 사용 가능 여부나 침해를 증명하지 않는다.

`central/support-email-connection.json`의 제출 값은 도입 당시부터 문서가 공개 배포를 명시했고, main에도 같은 64자 값이 남아 있다. 값의 원문은 보고서/테스트/로그에 기록하지 않았다. GitGuardian의 개별 사건 화면·정확한 매치 위치는 별도로 열지 않았으며, 사용자 제공 경로와 커밋의 추가 내역을 대조했다.

**분류: 의도적으로 공개한 제출용 capability. Google 계정 비밀번호/OAuth 비밀의 유출로 확인되지 않았다. 다만 중계의 제출 권한을 행사할 수 있는 값이므로 보안상 무해한 오탐이라고 처리하면 안 된다.** 공개 값을 다시 공개 값으로 교체하는 것만으로 발신자 인증 문제는 해결되지 않는다. 운영 중 무단 사용·자료 유출이 발생했다는 증거는 이번 조사에서 확보하지 않았다.

## 재현 결과와 변경

실제 운영 중계에는 요청하지 않았다. 실제 Central.gs를 Node VM에서 실행하고 Google의 MailApp/Properties/Lock/Utilities만 대체했다. 키와 보고서는 모두 합성이다.

저장소 고갈은 기본 설정만으로 반드시 발생한다고 재현한 것이 아니다. 이전 코드의 91일×20건 합성 계산은 약 427,785바이트였으며 플랫폼 500KB 이내였다. 이번 상한은 다른 속성과 이전 기록을 포함한 여유를 확보하는 방어다. 이전 기록을 이관하지 않는 새 400KiB 제한은 호환성 문제를 만들 수 있어, 해당 업그레이드 테스트도 포함했다.

`credentialsExcluded:true`는 알려진 필드·표기를 제거했다는 의미다. 임의의 문자열·인코딩된 비밀·자연어에 포함된 모든 이름을 완전히 탐지한다는 보장이 아니다. 수동으로 본문을 포함할 때 일반 본문은 보존하되 명시적인 인증정보 표기는 마스킹한다. 중계는 원본 요청 내용을 로그나 오류 응답에 출력하지 않는다.

## 남는 위험

- 공개 키만 가진 정상 설치와 공격자를 구분할 수 없다. 새 UUID·다른 내용·클라이언트 제공 식별자만으로 사용자별 rate limit을 구현해도 공격자는 식별자를 바꿀 수 있다.
- 비공개 키를 실제로 배포하기 전에는 예약 용량을 정상 설치가 사용할 수 없다. 공개 경로는 기존보다 처리량이 줄어든다. 이 변경만으로 자동 제보 가용성이 완전히 보장된다고 설명하지 않는다.
- 비공개 설치 키도 탈취되면 해당 제출 권한이 악용된다. 공유 비공개 키 대신 설치별로 발급·폐기한다.
- Apps Script 실행·속성 읽기·동시성 자원은 별도다. 공개 엔드포인트 대량 호출에 대한 네트워크 차원의 방어는 이 코드만으로 해결되지 않는다. 장기적으로는 등록된 설치 인증과 앞단 rate limit을 갖춘 별도 수신 서비스가 필요하다.
- 본문/이름 포함 플래그는 제출 데이터 최소화 옵션이며 제출자의 신원을 증명하지 않는다. 수신 첨부는 검증되지 않은 외부 입력이다.

## 배포·키 교체·기존 설치 호환성

이번 변경은 코드/테스트/PR이며 Apps Script 실제 배포, Script Properties 수정, 설치별 키 발급, 운영 전송 검증은 실행하지 않았다. 기존 공개 값은 바꾸지 않았다. GitGuardian 사건 상태도 변경하지 않았다.

1. 중앙 프로그램의 QUOTA 대기 변경을 먼저 배포한다. 구형 클라이언트도 같은 `{key,report}`와 영수증을 사용할 수 있지만 하루 대기를 이해하지 못하므로 더 빨리 재시도 횟수가 소진될 수 있다.
2. 운영자가 `Central.gs`를 기존 웹 앱 배포에 적용한다. `REPORT_KEY`는 호환용으로 유지하고 `REPORT_TRUSTED_KEYS`는 24~200자 설치별 비공개 키의 JSON 배열(최대50개, 속성 크기 제한 때문에 64자 키 권장)로 설정한다. 누락 시 빈 배열이며, 공개 키를 이 배열에 넣으면 CONFIG로 거절한다.
3. 비공개 키는 저장소·공통 배포 JSON·보고서에 넣지 않는다. 기존 인증된 제보 설정 경로로 해당 설치에만 등록한다. 새 설치의 gitignore 대상 `central/support-connection.json`은 초기 연결용으로 사용할 수 있으나, 기존 설치는 `connectionInitialized` 때문에 파일 교체만으로 키가 바뀌지 않는다. 자격 파일·전송함 전체 삭제로 이관하지 않는다. 사용자 동의도 유지한다.
4. 키별 영수증 공간이 다르므로 **전송 결과가 불명확한 대기 항목이 있는 동안 키를 변경하면 같은 보고서가 다른 키로 다시 발송될 수 있다.** 큐가 비고 미확정 결과가 해소된 설치부터 전환한다. 불명확한 기존 요청을 자동으로 성공 처리하거나 새 ID로 다시 만들지 않는다.
5. 구형 영수증에는 내용 지문이 없어, 기존 ID 재시도는 DELIVERY_UNCERTAIN을 돌려주고 재발송하지 않는다. 이미 접수 확인한 클라이언트에는 영향이 없지만, 배포 직전 응답 유실 상태의 항목은 관리자의 확인이 남는다. 새 영수증은 같은 키/내용의 응답 유실 재시도를 정상 처리한다.
6. 실제 비공개 설치 키 노출이 확인되면 해당 키를 목록에서 폐기하고 새 키를 안전하게 전달한다. 즉시 폐기는 구형 설치를 UNAUTHORIZED 상태로 만들며, 병행 허용은 노출된 권한을 그 기간 유지하므로 침해 정황에 따라 선택한다. 공개 REPORT_KEY의 단순 재발급은 인증 개선이 아니고 기존 설치만 끊으므로 수행하지 않았다.
공개 경로를 완전히 종료하려면 모든 필요한 설치 전환과 대기 항목을 확인한 뒤 REPORT_KEY를 제거한다. 이는 구형 공개 키 설치의 자동 접수를 중단하는 운영 변경이다.

7. 실제 Google 비밀번호/OAuth 비밀이 별도로 확인된다면 해당 인증수단을 별도로 폐기·재승인하고 사용 기록을 확인한다. 이번 제출 값의 교체로 Google 인증정보가 폐기되는 것은 아니다.
